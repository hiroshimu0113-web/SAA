今回の提案

「要件を満たす構成ほど勝ちやすい」ゲームにする。処理量、安全性、許容停止時間、データの鮮度、予算などを各ステージの条件にして、構成の選択に意味を持たせます。

「理想のインフラ」は用途によって変わります。SAAでも安全・回復力・高性能・費用最適化を考えて構成を選びます。ゲームもひとつの構成を常に最強にせず、条件に適合する複数の勝ち筋を推奨する案です。

根拠：SAA-C03試験ガイド / Well-Architectedの6つの柱。ゲームへの対応は本資料の設計提案です。

現実の構築手法は公式資料をもとに記述し、戦闘効果・ターン・負荷・費用の値は架空の教材モデルとして分けています。採用・ゲーム実装・独立した内容監査は未実施です。

勝敗と報酬を、構成選択へつなぐ

要件を読む→構成を選ぶ→負荷・障害を受ける→条件を満たして完了→費用・運用を比較

先に必須条件を判定

必要な仕事を期限内に完了できたか。保護対象を守ったか。復旧時間・損失・鮮度が許容内かを判定します。

安全性やデータ損失の未達を、攻撃力や余ったコインの点数で相殺しない案です。

適合した構成同士で比較

要件を満たした後に、維持費・使用資源・復旧の手数・運用の複雑さで報酬を比べます。同程度の構成には同程度の報酬を認めます。

重い構成を常に禁止せず、必要な冗長化や余力には正当な価値を持たせます。

現実の意味ゲームへ落とす案残す判断
処理能力・需要攻撃は必要な仕事を処理する力。敵HPを必要仕事量として扱う案。通常需要は攻撃ではない。期限内の完了と未処理量を確認。
可用性とデータ保全停止した処理枠、復旧待ち、成果の復元点を別々に持つ。HPひとつで停止時間とデータ損失を混ぜない。
安全性不正要求を防ぐ一方、正規要求を通す。すべて拒否して無傷でも業務を完了できない。
費用と使用資源行動エナジーとは別に、配置の維持費・処理の使用費を持つ。台数を増やすと継続支出も増える。価格は教材の仮定値。
観測敵の状態や負荷を把握し、適切な対処を選ぶ。観測があっても修復手段がなければ直らない。
資源効率・持続可能性単位仕事あたり使用資源を確認する。料金の安さだけで実際の環境負荷を断定しない。

これは将来のルール案です。現行のHP・3エナジー・通常30カードを今回変更するものではありません。持続可能性の考え方：負荷に適した効率的なインスタンス。

共通の基礎と、選べる特化を分ける

必要最小の権限、必要な通信、データ保護と保存、監視、復旧方針は各ビルドに必要な範囲で持たせます。「セキュリティビルドを選ばないと基本的な保護もない」という設計は避け、守る脅威や強化の方法に個性を持たせます。

保存時暗号化と認可は別です。S3は新規保存オブジェクトを標準で暗号化しますが、業務上のアクセス制御は引き続き必要です。SSE-KMSなら鍵使用の許可も確認します。

IAMのベストプラクティス / S3のサーバー側暗号化 / KMSキーポリシー

カード、役、ビルドをどう分けるか
  • カード：処理先、通信許可、観測、データ保存など、構成要素や行動を表す。
  • 役：局所的な連携。例：振り分け＋正常な処理先＋利用できるデータで、要求を処理できる。ただし固定3枚は現実の必須構成ではない。
  • ビルド：冒険全体で、負荷・障害・費用の条件に合わせて要素と対処を選ぶ方針。役を1つ揃えただけでは完成しない。

役の成立で無条件の火力を出すより、条件が揃った処理・切替・再開などの結果へ報酬をつなげます。実サービスの要件とゲームの枚数条件を分けて表示する案です。

前回のビルド案をどう読み替えるか

現実の意味ゲームへ落とす案残す判断
攻撃ビルド並列処理、Auto Scaling、読取分散で仕事を速く処理する。下流のボトルネック、起動待ち、維持費を残す。
要塞ビルド多層防御、複数AZ、障害隔離を別系統として扱う。侵害防止・停止対策・データ保全は同じ防御値にしない。
状態異常ビルド観測・原因判別・負荷制御・回復を、状態の扱いとして表す。AWSの正常なスロットリング等を敵意や必ず悪い状態にしない。
ギャンブルビルドSpot等の中断リスクを保存・再開・代替容量で管理する。確率で瞬殺して構築の不足を埋めるものにはしない。
魔法ビルドキャッシュ・事前処理で同じ仕事の計算や往復を省く案へ転換。認可・暗号化・防御を無視する能力とは結びつけない。
回復・復活バックアップ復元、切替、災害復旧へ対応。過去の成果損失、復旧時間、復元後の確認がある。
連撃・ループ・再使用分割処理、キュー、安全な再試行へ対応。無限連打は負荷増幅。重複した仕事の報酬は増やさない。
ドロー・サーチ観測・必要要素の確保・構成の組み立てへ対応。手札を増やすだけでは処理能力や復旧能力は増えない。
経済・圧縮適正容量、不要資源の削減、料金契約へ対応。契約割引は容量保証ではない。要件を落とす節約は失点。
召喚・複製処理枠の追加、テンプレートによる構成再現へ対応。追加枠は起動待ちと維持費があり、誤設定も複製される。

対応は設計上の再解釈です。前回の59案をそのままAWSの正しい構築法と認定するものではありません。

戦闘へ落とす、具体的なルール案

盤面に残る構成と、手札から使う対処を分ける。EC2等の処理先は配置として残り、毎ターン仕事を処理します。観測・増設・再試行・復元等は行動札として使う案です。何を配置しているかがビルドの姿になります。

カード名・構成要素名は教材由来の用語を使い、下の「処理枠」などは相談上の説明語とします。固定3枚役を揃えるだけで、要件達成と認定はしません。

以下は説明用の仮定数値で、採用数値・AWS性能・料金ではありません。現行攻撃値からの自動変換もしません。

  1. 要求量・期限・鮮度・次の障害を表示。
  2. 3エナジーで配置や対処を行う。増設は次ターンから有効。
  3. 障害で利用できない処理枠を反映。
  4. 有効枠で要求を処理。許可・データ・鮮度も検査。
  5. キュー期限、復旧待ち、成果保存を更新。
  6. 維持費を払い、次ターンへ。予算不足なら配置を維持できない。

仮定の基本値：処理枠1つで10仕事／ターン、維持費1／ターン。配置行動は1エナジー＋投資2、次ターンから使用可能。配置先のAZやデータ到達条件も持ちます。

ステージは必要仕事量と期限を持ち、復旧時間・許容損失・安全性・予算も提示します。処理完了と必須条件の適合でクリアし、適合後の支出を比べます。敵はサービス名より「AZ停止」「読取集中」「誤削除」などの課題として示す案です。

複数AZの構成例

需要20、AZ-Aに処理枠2つ、AZ-Bにも2つ。振り分けと両側で使えるデータを確保。

平常容量40、片AZ停止後も20。処理枠の維持費は4。各AZ1枠ずつなら維持費2ですが、停止後10となり未達です。

成立報酬は「残存容量で継続」。台数だけで防御を増やすものにはしません。

負荷追従の構成例

平常需要10で1枠。次ターン需要30を観測し、追加2枠を今ターン配置。

追加投資4、配置行動2エナジー、維持費は1から3へ増加。予告なしで今ターンに需要30が来ると、今の容量は10のままです。

キャッシュの構成例

原本と有効キャッシュを持つ。同じキーの読み取りは、初回取得後の2ターンだけ処理エナジーを1から0にする案。

更新で該当コピーを無効化。最新必須要求は原本確認が必要。条件付きの再利用で、全攻撃無料化にはしません。

キューの構成例

今ターン30仕事を受理し、毎ターン10処理。初回後の未処理20を保留し、合計3ターンで完了。

期限3なら適合、期限1なら未達。重複した仕事IDの再配送は成果を増やさず、冪等な処理で二重確定を防ぎます。

最小権限の構成例

EC2・S3・必要な読取許可を持つIAMロール・通信できる経路を組み、対象データを取得。

不足した許可では成功しません。全権限で動いても、不要な権限を使われる課題で損失が出ます。安全な正規処理を報酬にします。

バックアップの構成例

ターン2の成果を保存し、ターン4に誤削除。復元行動に2エナジー・1ターンを使い、ターン2時点へ戻る案。

ターン3以降の未保存成果は戻りません。許容損失を超えればHPが戻っても未達。短い保存間隔には保存費用を付けます。

各例の維持費や使用費は比較する構成ごとに明記します。例の数字を、実サービスの価格比較として使いません。

案 01 · 可用性

複数AZ・残存容量ビルド

狙い：1つのAZが使えなくても処理を継続する。

実際に向く条件：AZ障害が対象。切替先からデータを読め、障害後の容量が需要を満たす。

利用者 → ALB → AZ-A／AZ-Bの処理先 → 共有可能なデータ層

ゲーム効果の提案：

2つの独立した処理枠を持ち、片方の停止後も残る枠で攻撃＝処理を続ける。枠ごとに維持費を払う。

成立条件：配置だけでなく、正常先・利用可能なデータ・許可と経路・必要容量が揃った時だけ継続ボーナス。

ネック・代償：複数拠点の維持費と待機容量。監視・経路・データ層の設計も必要。

苦手な課題・代替案・キャラとの相性

現実の限界：同一AZへの偏り、容量不足、共有DBの停止で継続できない。リージョン全体の停止は別対策。

ステージ／敵の条件：AZ停止。複数AZを揃えても残存容量が不足すれば未処理が残る。

比較する別案：単一AZ＋復旧を許容する案／より広い障害には別リージョン。

前回案との対応：要塞・召喚・防御転換

キャラへの入口案：SRE／クラウドアーキテクト

構成選択の理由：正常先へ振り分ける仕組みと障害境界の分散を組み合わせる。

公式資料：ALBのヘルスチェック / VPCのインフラストラクチャ保護 / クラウドの災害復旧方式

案 02 · 性能・拡張

負荷追従ビルド

狙い：変動する需要に処理容量を追従させる。

実際に向く条件：並列化でき、状態を処理先の外に持てる。起動時間と上限を含めて計画する。

CloudWatchの負荷指標 → Auto Scaling → 処理先の増減

ゲーム効果の提案：

負荷に応じて次ターン以降の処理枠が増える。需要減少時は減らして維持費を回収する。

成立条件：観測指標・拡張方針・増設可能な処理枠・上限が揃う。追加枠は起動待ち後に有効。

ネック・代償：拡張までの待ち、増えたリソースの維持費、下流DBの限界。

苦手な課題・代替案・キャラとの相性

現実の限界：突然のピーク、誤った指標、容量上限やDB詰まりで追いつかない。

ステージ／敵の条件：突発負荷と持続負荷を別に出し、即時増設の誤解を崩す。

比較する別案：既知ピークの事前増設／最低容量を厚くする。

前回案との対応：攻撃・成長・エナジー

キャラへの入口案：クラウドアーキテクト

構成選択の理由：一定容量を常時買うより需要に合わせて調整しやすい。

公式資料：ターゲット追跡スケーリング / CloudWatchアラーム

案 03 · 性能・拡張

イベント駆動サーバーレスビルド

狙い：短い処理を要求時に実行し、サーバー管理の負担を減らす。

実際に向く条件：実行時間・同時実行・依存先の容量に収まり、状態と再実行を扱える。

イベント／API → Lambda → データ層

ゲーム効果の提案：

要求がある時に一時的な処理効果を発動。同時実行枠を超えると待ちや失敗になる。

成立条件：イベントと実行役と利用可能なデータが揃う。予約済み同時実行は上限枠、事前初期化は別効果。

ネック・代償：実行・要求・周辺サービスの費用、初期化遅延、クォータ。常に最安ではない。

苦手な課題・代替案・キャラとの相性

現実の限界：同時実行や拡張速度の上限で絞られる。DB接続や外部APIの上限にも詰まる。

ステージ／敵の条件：短い突発処理／長時間処理／コールドスタートに敏感な要求。

比較する別案：常駐EC2やコンテナ／遅延が厳しければ事前初期化を検討。

前回案との対応：生成・低コスト・追加行動

キャラへの入口案：クラウドアーキテクト

構成選択の理由：サーバーの台数管理を減らし、イベント単位で処理できる。

公式資料：Lambdaの同時実行と拡張

案 04 · データ高速化

エッジ配信ビルド

狙い：繰り返し参照するコンテンツを利用者に近い場所で配信する。

実際に向く条件：キャッシュできる要求で、キー・TTL・アクセス制御を設計する。

利用者 → CloudFront → ミス時にS3等のオリジン

ゲーム効果の提案：

同じデータ要求には低コストで処理。更新時は古いコピーを無効化する判断が必要。

成立条件：同一キーの要求・有効なコピー・鮮度条件を満たした時だけ割引。

ネック・代償：鮮度との調整、ミス時の負荷、配信・要求の費用。

苦手な課題・代替案・キャラとの相性

現実の限界：更新直後も古いキャッシュが残り得る。個別データの誤共有を避ける。

ステージ／敵の条件：同一内容の大量閲覧。常時変化する個別要求では利益が小さい。

比較する別案：オリジン直接配信／キャッシュ対象を絞る。

前回案との対応：低コスト・再使用・速攻

キャラへの入口案：SE／クラウドアーキテクト

構成選択の理由：キャッシュヒットでオリジンの処理と往復を減らす。

公式資料：CloudFrontのキャッシュ期限

案 05 · データ高速化

DBキャッシュビルド

狙い：よく読むデータの取得を速め、原本DBへの負荷を減らす。

実際に向く条件：再利用率があり、古さの許容と更新・無効化を定義できる。

アプリ → ElastiCache → ミス時に原本DB → キャッシュ補充

ゲーム効果の提案：

既読要求を省エナジー化。期限切れ・更新イベント後は再取得が必要。

成立条件：原本・キャッシュ・更新／失効方針が揃う。最新必須の要求は原本確認を省略しない。

ネック・代償：キャッシュの維持費、ミス時の追加往復、整合性の扱い。TTLだけで常に最新とはならない。

苦手な課題・代替案・キャラとの相性

現実の限界：失効が集中すると原本へ負荷が戻る。古い値を許せない取引を誤って通す。

ステージ／敵の条件：同じ読み取りの連打と、更新直後の読み取りを混ぜる。

比較する別案：原本の性能改善／読み取りレプリカ。

前回案との対応：圧縮・再使用・低コスト

キャラへの入口案：SE

構成選択の理由：原本への同じ読み取りを繰り返さずに済む。

案 06 · 可用性

DBフェイルオーバービルド

狙い：DB障害後に待機系へ切り替え、業務を再開する。

実際に向く条件：RDSの単一待機系を持つMulti-AZ DBインスタンスを対象にする。アプリの再接続も考える。

書込／読取 → 主DB → 別AZの同期待機系

ゲーム効果の提案：

成立条件：別AZ待機系・必要データ・アプリ再接続が揃った時に切替。

苦手な課題・代替案・キャラとの相性

現実の限界：待機系は通常の読取火力を増やさない。論理誤削除を過去へ戻す機能でもない。

ステージ／敵の条件：主DB停止。読み取り過多には別手段が必要。

比較する別案：読取拡張はレプリカ／Multi-AZ DBクラスター等を別評価。

前回案との対応：要塞・復活

案 07 · データ高速化

読み取り分散ビルド

狙い：読み取り需要を原本DBから分散する。

    非同期複製する読み取り先で、遅延・エンジンごとの制約を考慮する。

  12. VPCのインフラストラクチャ保護

  13. AWS WAFとShield

  14. S3 Versioning
    オブジェクトの世代保持により誤削除・上書きから戻せる。各世代の保存費用を考慮する。
  15. S3 Object Lock
    Versioning有効バケットの特定バージョンを保持し、モードと権限によって削除保護の条件が変わる。
  16. 再試行を制御・制限する
    バックオフ・ジッター・上限で再試行を制御する。無制限再試行は負荷を増幅する。
