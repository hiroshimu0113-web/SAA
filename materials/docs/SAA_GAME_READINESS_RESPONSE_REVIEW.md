## GQR-001：練習の未確定回答が結果では正解、履歴では未回答になる（P2）

対象：[`study-state.mjs` の submitStudy](../public/tower/study-state.mjs#L37)、[`study-ui.mjs` の session/finish](../public/tower/study-ui.mjs#L37)。

**通常の操作で再現可能な経路：**

1. 学習室で1問だけの練習を開始する。
2. 正解の選択肢を選ぶ。「回答を確定」は押さない。選択内容はchangeイベントでセッションに自動保存される。
3. 「練習を終了する」を押す。
4. 一覧から「保存した学習を開く」で提出済みの練習を見る。

終了処理はpracticeでは `submitted=true` にするだけで、未確定回答をrecordAnswerへ渡さない。一方、提出済みの結果と解説は `confirmed` を参照せず、保存された `answers` を採点する。このため「提出済み：1 / 1」「正解」と表示するが、回答履歴は0件、当該問題は未回答のままである。複数問を順に学ぶ場合も、未確定のまま次へ移った問題で同じ不整合が生じる。

状態関数の実行で `confirmed=[false], records.length=0, submitted=true` を確認した。結果表示の採点式では当該回答が正解となる。画面でのクリックによる再現は今回未実施だが、終了ボタンが未確定状態でも表示され、当該処理へ接続することをコードで確認した。

**修正・受入条件：** 練習終了時の未確定回答の扱いを統一する。終了時に有効な回答を確定・履歴保存する、または未確定を正解数へ加算せず明示する。どちらの場合も、結果・解説・履修数・初回/直近成績が同じ回答状態を表すこと。1問練習と途中の未確定回答、再開、終了後の再保存で重複記録がないことを確認する。

## GQR-002：提出済み結果と履歴が矛盾するバックアップを受理する（P2）

対象：[`study-state.mjs` の parseStudy](../public/tower/study-state.mjs#L12)、[`study-ui.mjs` の読み込みと成績表示](../public/tower/study-ui.mjs#L34)。

`parseStudy` は各recordの正誤や選択肢添字、セッションの表示順等を検査する。しかし、提出済みassessmentセッションと対応するattempt/recordsの照合、attempt IDの一意性を検査しない。読み込み画面はこの検査を通ったデータで既存記録を置き換える。

**実行して確認した再現：**

- 65問全問正解で提出した正規データを作り、`records=[]` に変更しても `parseStudy` は受理する。保存したセッションの結果は65 / 65、一覧の受験履歴は0 / 65になる。
- 同一IDのattemptをもう1件加えても受理する。同じ受験が複数回として表示され、初回/再回答の履歴が不整合になる。

これは学習者の自己申告を保証する機能や、整合した手作りデータによる改ざんを防ぐ要求ではない。構造上は正しいJSONでも、内部で矛盾する結果・履歴を「正しいバックアップ」として既存記録へ取り込んでしまう問題である。

**修正・受入条件：** attempt IDの重複を拒否する。少なくとも保存中の提出済みassessmentについて、対応attemptの終了状態と、各設問の回答記録の存在・問題版/スナップショット・選択内容を照合する。セッション終了後のattemptにも、現在の保存形式で可能な範囲の記録整合性を検査する。不整合な読み込みで元記録を上書きしないこと。正規の途中/提出済み/終了後バックアップと旧教材版は引き続き復元できること。
