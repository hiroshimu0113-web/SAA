# 教材をカードとゲームへつなぐ分類ガイド

教材を収集・作成・改訂するエージェントは、このガイドに従って学習内容を分類し、再利用できる形で記録する。対象は用語、概念、システム、役、ビルド、クイズ用のケースシナリオ。カード、役、新キャラクターは分類済みの教材から設計する。

**分類はサービス名ではなく、何を理解してもらうかで決める。** ゲームでは条件に合うAWS構成を選ぶ力を育てる。単語の暗記、役の成立、プレイ回数だけを理解の証拠にしない。

ガイド版 2。2026年10月6日制定。教材本文の正本は既存の知識単位・教材ファイル、ゲーム利用の分類は [収集台帳](../knowledge/game-classifications.json) を正本とする。台帳は収集用の形式であり、現行ゲームへ直接読み込むインポーターはまだない。

## 教材作成時の作業順

1. [知識データの案内](../knowledge/README.md)、棚卸し、拡充計画と本ガイドを読む。収集台帳と既存IDから重複を探す。
2. 一つの判断・説明に学習目標を絞る。複数の目標が混ざる場合は、同じ出典でもレコードを分ける。
3. 主分類を一つ決め、分類理由を書く。分野・能力・ゲーム用途のタグを別々に付ける。
4. 定義だけでなく、働く条件、働かない条件、代償、混同しやすいものを収集する。無料で読める公式資料を主な根拠にする。
5. 収集台帳の `items` へ追加・更新する。教材本文を台帳へ丸ごと複製せず、元ファイルと単位IDを参照する。
6. 分類別の必須項目を確認し、内容の正確性とゲームでの表現を別々にレビューする。未解決点は残し、根拠なく状態を引き上げない。
7. 作成・変更した分類ID、保留理由、検証結果、次の作業をCHECKPOINTとTASKSへ記録する。教材だけ更新して分類を後回しにしない。

既存教材は今回一括で分類済みにしない。今後触れる範囲から、同じ手順で分類を追加する。ゲーム用途が見つからない教材も削らず、`deferred` と理由を記録する。

## 主分類の六つの基準

主分類 `kind` は一レコードにつき一つ。分類名は次の英語キーで固定する。

| 主分類 | キー | 学習者ができるようになること | 収集時に必要な情報 |
|---|---|---|---|
| 用語 | `term` | 名前と意味を対応させ、似た名前と区別する | 正式名称、略称・別名、短い定義、範囲、混同対象 |
| 概念 | `concept` | 原理や設計上の性質を説明し、条件に適用する | 原理、成立条件、反例、比較対象、判断基準 |
| システム | `system` | 要素がどう連携して働くかを追える | 要素の役割、入力、処理や通信の流れ、出力、依存条件、異常時の動き |
| 役 | `combo` | 複数要素の連携をカードの組み合わせとして説明する | 構成カード、実際の連携理由、成立条件、追加効果、回数制限、省略と誤学習リスク |
| ビルド | `build` | 要件に合う構成を選び、代償を説明する | 目的、要件・予算等の制約、採用要素、代替案、選ぶ理由、弱点・維持費 |
| ケースシナリオ | `case` | 具体的な状況から判断し、理由を示す | 状況、既知の条件、問い、選択肢、正解条件、各誤答の理由、条件を変えた問い |

「用語」は一語で表せるという意味だけではない。名前を知ることが学習目標なら用語、原理を理解することが目標なら概念にする。概念もカード化でき、用語もカード化を見送れる。

「役」は複数カードの局所的な連携と発動ルール。「ビルド」は冒険を通して選ぶ構成方針であり、役を一つ揃えることだけとは区別する。`kind=combo` は役そのものを記述するレコード、`game_targets` の `combo` は他分類の教材を役へ使う候補である。

「システム」はAWSサービス名の別名ではなく、連携の仕組みを扱う分類。「ビルド」はその仕組みを特定の目的と制約のために選んだ構成。複数サービスが出てくるだけでビルドとはしない。

## 迷ったときの判定順

- 特定の状況に対する問いと正解条件があるなら `case`。
- カードの組み合わせによる発動条件と追加効果を定義する資料なら `combo`。実際の仕組みを説明する `system` とは関連付けて分ける。
- 目的・制約・選択理由・代替案まで扱うなら `build`。
- 要素間の因果関係や動作の流れが主題なら `system`。
- 原理、性質、設計判断が主題なら `concept`。
- 名称と定義の対応が主題なら `term`。

複数に該当するときは、問いを分けて別IDで関連付ける。分類を決められる情報が不足していれば、暫定の主分類と理由を付け、`classification_status` は `draft`、不足を `open_questions` に残す。名前だけを見た自動分類は確定扱いにしない。

## 同じテーマを分類し分ける例

以下は収集する学習目標の例であり、AWS構成の検証済み設計書ではない。

| 学習目標の例 | 主分類 | 判定理由 |
|---|---|---|
| ALBという略称と正式名称を対応させる | 用語 | 名前の識別が目的 |
| 負荷分散の目的と限界を説明する | 概念 | 特定製品の手順より原理が中心 |
| ALBの振り分けとヘルスチェックの流れを追う | システム | 要素間の動作と例外の理解が中心 |
| 負荷分散・並列処理・観測の3カードで役が成立する理由と条件を説明する | 役 | 仕組みをゲームの組み合わせと報酬へ対応させる |
| 所定の負荷・障害・費用条件を満たすWeb構成を比較して選ぶ | ビルド | 要件に応じた選択と代償を扱う |
| ある障害後に処理を継続できる構成を選び、理由を答える | ケースシナリオ | 状況と採点条件を持つ問い |

これらを一つのALBレコードへ詰め込まない。用語からシステム、ビルド、ケースへの参照をつなぐ。既存の `alb` 等の知識単位は参照し、分類の都合だけで既存IDの意味を変えない。

## タグの軸を分ける

`kind` 以外は複数指定できる。対象に根拠のあるタグだけを付ける。難易度やゲームの強さを分類名に混ぜない。

| 軸 | 固定値と使い方 |
|---|---|
| `domains` | `compute`, `networking`, `storage`, `database`, `security`, `observability`, `integration`, `operations`, `cost` から選ぶ |
| `capabilities` | `process`, `store`, `route`, `observe`, `protect`, `recover`, `scale`, `coordinate`, `optimize`。何を担う内容かを表す |
| `concerns` | `availability`, `durability`, `performance`, `cost`, `security`, `operability`。何を評価する内容かを表す |
| `game_targets` | `glossary`, `card`, `combo`, `build`, `case`, `character`。将来の利用先候補であり、実装済みの意味ではない |
| `character_families` | 当面は `resilience`, `elasticity`, `data_acceleration`, `event_driven`, `access_control`。将来のプレイ傾向をまとめる仮の系統。未定は空配列 |

`domains` と `game_targets` は一つ以上。他の軸は必要な場合だけ付ける。サービス名は `service_names` に正式表記で記録する。既存知識単位の `group` や教材の `conceptIds` を、このタグで置き換えない。

新しいタグが必要なら本ガイドの語彙表へ定義と既存タグとの差を追加してから使う。大文字小文字違い、複数形、翻訳違いを別タグとして増やさない。別名は `aliases` にまとめる。

ゲーム上の「攻撃」「防御」「ドロー」は `game_design` へ記録する。例えば `compute` だから必ず攻撃カード、と自動変換しない。

## 収集レコードの共通項目

台帳の形は `{"schema_version":1,"items":[]}`。`items` 内は下のテンプレートに沿って記録する。未定を架空の値で埋めず、空配列または `null` と不足理由を使う。分類の形式検査は内容監査の代わりにならない。

| 項目 | 記録する内容 |
|---|---|
| `id`, `title`, `aliases` | 安定したID、表示名、別名。IDは `kind-topic-goal` の英小文字とハイフンで一意にする |
| `kind`, `classification_reason`, `objective` | 主分類、判定理由、一つの学習目標 |
| `unit_ids`, `material_refs` | 既存知識単位IDの配列と、`{path, locator}` の配列。pathはmaterialsからの相対パス、locatorは見出しや教材ID。存在しない参照は入れない |
| 五つのタグ軸と `service_names` | 上の語彙に従うタグとサービス名 |
| `prerequisites`, `conditions`, `limitations`, `misconceptions` | 前提知識、成立条件、限界・代償、誤解。必須条件と推奨条件は区別して文章にする |
| `content` | 主分類ごとの詳細。下の必須項目に従う |
| `relations` | `{type, target_id, reason}` の配列。参照先は台帳内のID。方向と理由を書く |
| `sources` | `{url, claim, checked_on, reviewer}`。どの主張を照合したかを記録。未照合の日付・担当はnull |
| `classification_status` | `draft` または `reviewed`。分類理由・タグ・参照の確認状態 |
| `content_status` | `draft`, `reviewed`, `needs_revision`。説明や解答の内容監査の状態 |
| `game_design` | 利用案、ゲーム上の省略、想定される誤学習、実装参照等 |
| `review_notes` | `{scope, reviewer, checked_on, summary}` の配列。scopeは `classification`, `content`, `game`。担当・日付・確認内容を残す |
| `import_status`, `open_questions` | `candidate`, `ready`, `imported`, `deferred` と未解決事項。分類済みでもすぐ取り込まない |

`prerequisites`, `conditions`, `limitations`, `misconceptions`, `open_questions` は文章の配列とする。`sources` は主張ごとの根拠、`review_notes` はレビュー作業の証跡として分ける。IDは表示名が変わっても維持し、統合・廃止する場合は旧IDからの対応を記録する。

関係 `type` は `prerequisite_for`（前提→学ぶ先）、`part_of`（要素→仕組み）、`used_in`（概念や仕組み→ビルド）、`assessed_by`（対象→ケース）、`alternative_to`（比較する相手）とする。`alternative_to` は対称の意味だが二重登録は不要。学習の前提関係と、AWSの技術的依存関係を混同しない。

既存の `knowledge/relations.json` は別の契約を持つ。台帳の関係をそのまま転記せず、既存形式への意味の対応を確認する。

## 主分類ごとの詳細項目

`content` には次の項目を入れる。本文の重複を避ける場合は、説明項目を `{path, locator}` で既存本文へ参照させてもよい。収集中の不足は `open_questions` に明記し、内容監査完了までに埋める。

- `term`：`definition`, `distinguish_from`。別名は共通の `aliases` に記録。
- `concept`：`principle`, `applicable_when`, `counterexample`, `comparison`。
- `system`：`components`（名前と役割）, `input`, `flow`, `output`, `dependencies`, `failure_behavior`。
- `combo`：`card_ids`, `real_world_relation`, `trigger`, `reward`, `repeat_limit`, `reset`, `system_refs`, `counterexample`。実装済みカード/役IDは正確に参照し、実AWSの要件とゲーム上の3枚条件を区別する。
- `build`：`goal`, `constraints`, `components`, `selection_reason`, `alternatives`, `tradeoffs`, `failure_behavior`。費用は維持費や運用負担を含め、実価格を使う場合はリージョン・時点・前提を明記。
- `case`：`premise`, `constraints`, `questions`, `variant`。ケースの記入基準は次節に従う。

複数要素を列挙しただけの資料は、連携が分かるまで `system` のレビューを完了しない。「高可用性だから良い」のように要件や比較対象がない構成は、`build` として不足がある。

## ケースシナリオをクイズに使う基準

一ケースは一つの状況を扱い、現在の「?」マスへ取り込む場合は2問を用意する。第1問で構成や対処を選び、第2問で理由や条件変更後の判断を問うと、暗記だけに偏りにくい。第2問の正解に第1問の正解を前提とさせず、誤答しても回答可能にする。

各問には `id`, `objective`, `prompt`, `options`, `correct_option_id`, `rationale`, `source_urls` を記録する。`options` の各要素は `{id, text, explanation}`。現行UI向けは単一正解・3択とし、選択肢の配列位置ではなく固定IDで正解を保管する。ランタイムへの変換時だけ位置へ変換する。

取り込み時には `runtime_option_order` に表示順の選択肢IDを固定する。現行保存形式が選択肢番号を保持するため、取り込み済み問題のこの順番・ID・正解の意味は維持する。本文の配列順の変更だけで保存済み回答を再解釈しない。意味を変える改訂は新しい問題IDで扱う。

- 状況、負荷、保護したい対象、障害範囲、予算等のうち、正解を決める条件を明示する。
- データ同期済み、残存容量十分など、判断を左右する前提を省かない。条件不足で複数正解になるなら問題を直す。
- 全選択肢に理由を付ける。誤答は単に「非推奨」ではなく、どの条件を満たさないかを示す。
- 架空の数値は仮定と明記し、AWSの性能保証と混同させない。
- `variant` には変更する条件、正解がどう変わるか、その理由を記録する。本文を少し言い換えただけの再出題にしない。
- 同じ用語の言い換え2問だけで、説明・適用・転移すべてを評価済みにしない。

現行 `public/tower/quiz.mjs` は既存4問の抽選と、確認済みの連続2問ケースを扱う。ケースの正本は `knowledge/game-cases.json`。`pnpm game-content:export` で確認済みだけを `public/tower/case-quizzes.mjs` へ生成し、`pnpm game-content:check` で照合する。新規抽選はケース内の順番を維持し、保存は既存の2問ID形式を維持する。既存問題のID・選択肢・正解順は保存互換性のため保持する。

## カードと役へ取り込む基準

カード候補は「一枚でどの要素を表現するか」を短く説明できること。実際の仕組みとカード効果の対応、省略した条件、比喩が通用しない境界を `game_design` に記録する。名称だけ一致する無関係な効果を割り当てない。

役候補は、要素同士が連携する理由を説明できること。`game_design` に候補カードID、成立条件、回数制限、報酬案、実際の関係との違いを書く。現行ゲームは異なる3種類を同一ターン・順不同・各役1回で判定するが、実AWSの必要要素を「3つ」に合わせて省略しない。カードで複数要素をまとめた場合は、その内訳を明示する。

単体カードでも使える価値を残し、組み合わせで追加の選択肢が生まれるようにする。成立の難しさ、必要エナジー、ドローへの依存、他の役との競合はゲーム側で試験する。教材の内容監査が通っても、数値バランスまで確認済みとはしない。

現行の「インシデント対応」「負荷分散構成」「キャッシュ活用」はゲーム上の比喩。これらのカード名をAWSの正式な構成要件として教材へ逆輸入しない。特に「防壁」のような抽象名を、根拠なく特定サービスと同一視しない。

## 効果と用語の説明・補足を分けて収集する

カード用の `game_design` には `mechanism_note`, `metaphor_limit` を持たせる。本文を別ファイルで管理する場合は、この2項目を `{path, locator}` の参照とし、同じ文章を台帳へ重複転記しない。

- 効果はゲームエンジンの数値を正本とし、説明側へ固定数値を埋め込まない。
- 詩的な創作文や雰囲気づくりのフレーバーは収集・表示しない。ユーザーの「フレーバー」は用語の説明・補足を意味する。
- `mechanism_note` は仕組みや運用上の考え方の短い補足。重要な条件・例外を詩的な文章だけに隠さず、公式出典と結ぶ。
- `metaphor_limit` はカードの効果と現実が一致しない部分。エナジー回復、攻撃、防御の数値が実AWSの性能や保証ではないことを具体的に示す。

説明・補足は独立した主分類ではなく、分類済みの用語・概念・システム・役を伝える表現。表示はカード詳細で効果と併記し、小さい手札には載せない。役にも同じ分離を適用できる。

## ビルドから新キャラクターへつなげる基準

`character_families` は候補を集計するためのタグであり、キャラクターの自動追加条件ではない。カード枚数だけで新キャラを作らず、次を確認する。

- 既存キャラと異なる判断や資源の使い方がある。
- 単体で機能する基本カードと、複数の役・ビルドへの分岐がある。
- 得意な条件だけでなく、苦手な条件・費用・代償が説明できる。
- 一つの必須カードや固定コンボだけに依存しない。
- 学習目標、役、ビルド、ケースがつながり、条件変更への適応を学べる。
- 試遊で難易度と選択肢を確認し、既存キャラの単純な上位互換になっていない。

例えば `resilience` は障害への備え、`elasticity` は負荷変動への対応を中心に集める仮の系統名として使う。タグ名自体はAWSの正式分類ではない。

## 記入テンプレート

以下は収集台帳の一要素の書式例。山括弧部分を置き換え、主分類別の `content` を記入する。実在しない単位IDやURLを仮の参照として登録しない。

```json
{
  "id": "concept-example-goal",
  "title": "<学習対象>",
  "aliases": [],
  "kind": "concept",
  "classification_reason": "<なぜ原理や判断を学ぶ内容なのか>",
  "objective": "<条件を与えたとき、何を説明または選択できるか>",
  "unit_ids": [],
  "material_refs": [],
  "domains": ["operations"],
  "capabilities": ["observe"],
  "concerns": ["operability"],
  "service_names": [],
  "game_targets": ["card"],
  "character_families": [],
  "prerequisites": [],
  "conditions": [],
  "limitations": [],
  "misconceptions": [],
  "content": {
    "principle": "<原理>",
    "applicable_when": "<適用条件>",
    "counterexample": "<適用できない例>",
    "comparison": "<混同対象との違い>"
  },
  "relations": [],
  "sources": [],
  "classification_status": "draft",
  "content_status": "draft",
  "review_notes": [],
  "game_design": {
    "proposal": "<カードや役への利用案>",
    "mechanism_note": null,
    "metaphor_limit": null,
    "simplifications": [],
    "mislearning_risks": [],
    "implementation_refs": []
  },
  "import_status": "candidate",
  "open_questions": ["<出典照合や条件の不足>"]
}
```

`reviewed` へ変更するときは対応するscopeの `review_notes` が必要。内容レビューでは関連主張の公式出典も照合する。`ready` には分類・内容の両レビューと利用先の必須情報が必要。`imported` は実装ID・ファイルを `implementation_refs` に記録し、変換・ゲーム動作を検証してから付ける。教材の公開状態、知識単位の `review.status`、本人の理解状態は別管理で、自動的に連動させない。

## 保存と検証の境界

既存の `knowledge/units.schema.json` は未知の項目を許可しないため、タグを `units.json` に直接足さない。新たな知識単位が必要なら既存の手順で追加し、そのIDを台帳から参照する。生成物の `public/knowledge/graph.json` や棚卸しを手で書き換えない。

台帳は専用JSON Schemaを持たないが、`pnpm classification:check` でJSON、IDの一意性、固定語彙、単位・ファイル・関係参照、分類別項目、レビュー/取り込み証跡を検査する。本文の正確性やlocatorの意味は担当者が確認する。`pnpm knowledge:check` は既存知識データの検査であり、この台帳の合格証明ではない。

分類だけならゲームへの取り込み・配信変更は不要。知識正本を変えた場合は既存手順の `pnpm knowledge:export` と `pnpm knowledge:check`、実装を変えた場合は該当するテストとブラウザー検証を実施する。

## 提出前の確認

- 一レコードに一つの学習目標と主分類があり、理由が読める。
- 別名・既存IDを確認し、同じ内容を新規項目として増やしていない。
- 成立条件、反例、代償、誤解があり、単語の羅列で終わっていない。
- 出典のURLだけでなく、照合した主張・日付・担当が記録されている。
- 実AWSの関係とゲームの省略を区別し、役のために誤った依存関係を作っていない。
- ケースの正解が与えた条件から決まり、全誤答の理由がある。
- 未監査・未実装・本人未評価を混同せず、次の作業が引き継げる。
