# 教材の細分化と理解のナレッジグラフ

**教材を増やす前に、1つずつ何を理解させるかを定義するための作業基盤です。本人の理解度を表すグラフではありません。** 最初の型として、写真工房の音声・ゲームと先行教材につながる14単位を作りました。残りの原稿は棚卸しだけで、細分化・監査済みとは扱いません。

## ゲーム利用を見据えた教材分類

教材の収集・作成・内容改訂前に [分類ガイド](../docs/CONTENT_CLASSIFICATION_GUIDE.md) を読み、[収集台帳](game-classifications.json) へ記録します。主分類は用語・概念・システム・役・ビルド・ケース。ゲーム用途やキャラ系統は別のタグです。既存の units.json と relations.json の契約は維持し、台帳はゲームへ直接読み込む形式ではありません。既存教材の一括分類とインポーターは未実施です。

## 入口

- [理解の地図（対話表示）](https://hiroshimu0113-web.github.io/SAA/knowledge/index.html)：概念を選ぶと前提・確認問題・誤解・教材との関係を表示。
- [units.json](units.json)：手で更新する14個の細分化単位。1単位に1つの判断目標を置き、説明と適用の確認を各1問用意。
- [units.schema.json](units.schema.json)：後続の制作者が使うJSON Schema。レッスン参照や循環などは生成時にも検証。
- [relations.json](relations.json)：混同しやすい概念と、組み合わせる概念の関係。
- [INVENTORY.md](INVENTORY.md)：全12章・36レッスン・200問の棚卸し。公開範囲は2章6レッスン・20問。
- [graph.json](../public/knowledge/graph.json)：自動生成する407ノード・609エッジのスナップショット。数は教材更新で変わる。
- [EXPANSION_PLAN.md](EXPANSION_PLAN.md)：内容を厚くする順序と引き継ぎ。

## 「理解」を分ける型

| 観点 | 具体的に確認すること | 記録方法 |
|---|---|---|
| 説明 | たとえを離れて正式な仕組みを言える | `checks.level=explain` と必要な回答要素 |
| 適用 | 条件を読んで構成を選び、理由を言える | `checks.level=apply` と必要な回答要素 |
| 区別 | 紛らわしい選択肢が不適合な理由を言える | `misconceptions` と `contrast_with` |
| 転移 | 条件を1つ変えても判断し直せる | 次の拡充で追加。現在の2問だけでは判定しない |

5分は教材の設計目安で、習得までの保証時間ではありません。正解番号の暗記、音声の再生完了、ゲームの星、ファイルの存在を理解の証拠にしません。

## 3種類の状態を混ぜない

1. **教材の公開状態**：レッスン・問題の `release=published/draft`。`src/content/index.ts` に基づく。
2. **細分化単位の監査状態**：`review.status=draft/reviewed`。現在の14単位はすべてdraft。旧教材の監査済み表示を新しい確認問題へ引き継がない。
3. **本人の理解状態**：共有グラフではすべて `unassessed`。本人の回答がないため未評価。

実際の学習観察を残す場合は、[空テンプレート](learner-observations.example.json)を非公開の保存先へコピーします。観察にはunit_id、check_id、回答原文、日時、確認した回答要素、未充足の要素、レビュー担当を残します。公開リポジトリへ個人の回答を入れないでください。1回の回答から長期定着や別条件への転移まで推定しません。

## グラフの読み方

| 関係 | 向きと意味 |
|---|---|
| `learn_before` | 前提の概念 → 次の概念。教材設計上の推奨順であり、AWSの必須構成ではない |
| `contrast_with` | 違いを説明したい2概念。意味は対称 |
| `used_with` | 事例で組み合わせる2概念。必須依存を意味しない |
| `covered_by` | 概念 → 既存conceptIdsで関連付けられたレッスン。タグ自体は未監査を含む |
| `unit_reference` | 概念 → 今回の細分化に使ったレッスン。既存タグにない本文中の説明も含む |
| `practised_by` | 概念 → 既存問題。公開・原稿状態を必ず確認する |
| `reinforced_by` | 概念 → 5分音声。聞いただけで習得したとは扱わない |
| `applied_in` | 概念 → ゲームのミッション。単一概念を独立に測定できるとは限らない |
| `contains` | 章 → レッスン／問題 |

図は14単位とlearn_beforeだけを表示し、その他の関係は詳細欄で見ます。機械用JSONは教材全体の概念IDも保持します。155個の概念IDには表記揺れや複合タグの可能性があり、155個の完成済み知識単位という意味ではありません。名前だけで自動統合しないでください。

## 後続エージェントの作業順

1. CHECKPOINT、CONTENT_REVIEW、INVENTORY、EXPANSION_PLANを読む。`units.json`を正本とし、生成されたgraph.jsonを直接修正しない。
2. 対象を1つの判断に絞り、安定した概念IDを選ぶ。既存IDの意味を変える場合は対応表を残す。
3. 目標・前提・説明問題・適用問題・誤解・教材参照を作る。最初はdraftとする。
4. 無料のAWS公式資料で各主張と例外を確認する。日付だけでなく対象主張・URL・レビュー担当を記録する。reviewedにはevidenceが必要。
5. 別のレビュー工程で正解が一意か、未習前提が混入していないか、誤答の理由が説明できるかを確認する。
6. `pnpm exec tsx scripts/export-knowledge.ts` → `pnpm test` → `pnpm build`。図を変えたら `CHROME_PATH=/usr/bin/chromium node scripts/knowledge-browser-check.mjs`。
7. 生成差分と台帳を確認する。単位の追加はアプリ教材の公開範囲を自動的に変えない。

## 検証の限界

生成時に重複ID・参照先・前提の循環・評価の形式を検査します。自動検査はAWSの説明が正しいこと、試験範囲を網羅すること、学習者が理解したことの証明ではありません。現在の既存source.checkedは転記であり、今回オンラインで全155概念を再監査したわけではありません。
