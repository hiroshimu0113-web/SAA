# 一時認証情報：期限と権限を分ける

学習目標：長期キーをコードへ埋め込まずに認証情報を取得し、期限があっても権限を絞る必要を説明する。既存単位 `temporary-credentials` の本文。関連章：ch02、ch04、ch08、ch10。

## 仕組み

AWS STSのAssumeRoleは、アクセスキーID、シークレットアクセスキー、セッショントークンを含む一時認証情報を返す。キー2項目だけを長期キーと同じように扱うと、セッショントークンを欠いた認証になる。有効期限と「何をしてよいか」は別の条件で、短命でも広い権限を与えれば有効な間はその操作が可能になる。

EC2上のアプリではインスタンスロールの認証情報をIMDSから取得するSDKのプロバイダーを利用できる。固定キーを埋め込む運用から、実行環境に対応する認証情報の取得へ切り替える。IMDSはEC2のインスタンスメタデータを取得する仕組みで、S3の保存先そのものではない。

流れ：EC2のロール → IMDS → SDKの認証情報プロバイダー → 認証情報を使ってS3へ要求 → 権限評価。EC2でロールの認証情報を取得する処理を、アプリが毎回明示的にAssumeRoleする処理と同一視しない。

## 適用条件と限界

- EC2に必要なロールを用意し、アプリからIMDSに到達できることが前提。インスタンスプロファイルとの関連付けは次のIAMロール単位で扱う。
- SDKの認証情報探索で別のプロバイダーが先に選ばれる場合、EC2のロールが自動的に選ばれるとは限らない。固定キーの設定を残したままロールを付けて完了としない。
- 期限を持つ認証情報は、期限切れ前後の再取得を考える必要がある。SDK・プロバイダー・キャッシュの設定に依存するため、取り出した値を自作の永久キャッシュへ保存しない。
- AssumeRoleのセッションポリシーはロールの権限を広げない。ロールのIDベースポリシーとセッションポリシーの共通範囲に制限する。SCP、リソースポリシー、明示的Deny等を含む評価全体はこの単位の範囲外。
- APIのセッション期間とEC2ロール認証情報の更新を一律の固定時間として教えない。漏えいした一時認証情報にも有効な間のリスクがある。

## 比較

| 対象 | 役割 | 混同を避ける点 |
|---|---|---|
| 一時認証情報 | API要求で主体を示す期限付きの値 | 短命というだけで全操作を許可しない |
| IAMロール | 信頼と実行権限を定めるIAMの主体 | ロール自体をアクセスキーと呼ばない |
| セッションポリシー | AssumeRoleのセッション権限を制限 | ロールにない権限を追加できない |
| 固定キーを埋め込む構成 | アプリへキーを直接配布 | コードや設定へ配布したキーの管理が残る |

## 確認と転移

説明問題：一時認証情報の3項目と、期限だけでは最小権限にならない理由を説明する。回答要素は `units.json` の `temporary-credentials-explain`。

適用ケースは `knowledge/game-cases.json` の `temporary-credentials-photo` を正本とする。2問で固定キーを避ける取得方法と、期限内でも許可されていない操作を区別し、全選択肢に理由を用意する。

条件変更：EC2のアプリではなく、すでにAssumeRoleで得たセッションを使うクライアントの権限を読み取りだけへ絞りたい。ロールがGetObjectとPutObjectを許可していても、セッションポリシーでGetObjectに制限すればPutObjectを追加付与することにはならない。EC2のIMDSプロバイダーをそのまま別環境へ適用する回答は不適合。
