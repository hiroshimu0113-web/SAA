# 認証：要求に使われた主体を確認する

学習目標：誰として要求したかの確認と、その主体に許可される操作を分ける。既存単位 `authentication` の本文。関連章：ch02、ch04、ch10。

## 仕組み

認証は主体の確認、認可はその主体の操作を許可するかの判断である。画面へログインできたことや、APIで主体を確認できたことを、その後の全操作の許可と同一視しない。

AWS STSのGetCallerIdentityは、呼び出しに使われた認証情報のIAMユーザーまたはロールに関する情報を返す。Accountはその主体を所有・包含するアカウント、Arnは呼び出し主体のARN、UserIdは主体の種類に応じた識別子である。ARNはリソースや主体を識別する名前で、シークレットアクセスキーではない。このAPIは呼び出し主体を調べる入口になり、S3を保存できるかの権限試験の代わりにはならない。

流れ：アプリが認証情報プロバイダーを選ぶ → その認証情報でGetCallerIdentityを呼ぶ → Account/Arnを意図した主体と比較する → 実行したい対象操作の認可は別に確認する。

## 特別な動作と限界

GetCallerIdentityには操作権限が不要で、sts:GetCallerIdentityを明示的にDenyするIDポリシーがあっても同じ主体情報を得られると公式API説明に記載されている。これはこの操作の特別な性質で、S3等の操作にもDenyを無視できるという一般則ではない。ネットワーク到達性や有効な認証情報まで不要になる意味でもない。

EC2のSDKで別の認証情報プロバイダーが先に選択された場合、期待していたEC2ロールと異なる主体が要求を行うことがある。ロールを付け直す前に、実際に選ばれたプロバイダーや固定キー設定を確認する。認証情報そのものを調査ログへ出力する必要はない。

## 比較

| 確認 | 得られる判断 | 判断できないこと |
|---|---|---|
| GetCallerIdentity | 要求に使われた主体とアカウント | S3等の操作が許可されるか |
| ロールの信頼・呼び出し元のAssumeRole許可 | ロールを引き受ける条件 | 引き受け後の任意の操作許可 |
| 対象操作のポリシー評価 | 対象・操作・条件の許可 | そのポリシーを評価する前の主体選択が意図どおりか |
| MFA | 別要素を用いた認証の確認 | 最小権限の設計そのもの |

## ケース・転移・確認

`knowledge/game-cases.json` の `authentication-caller-identity` が正本。第1問は主体情報と操作権限を分け、第2問はGetCallerIdentity固有のDenyの扱いを一般化しない理由を問う。どちらも有効な認証情報と正常な通信を前提にする。

条件変更：返されたAccountが想定と違う。調べる対象は実際の認証情報選択であり、S3の操作許可を増やしても呼び出し主体そのものは変わらない。

説明問題は認証と認可の役割。適用問題はMFAでログイン後にS3へアクセスできない場面で、認可・通信などを分けて調べる。MFA成功だけでS3成功を保証しない。応答や実行履歴の存在だけで本人がこの違いを理解したとは評価しない。
