# AWS Configの記録済み構成・評価・修復

## 仕組み

AWS Configルールは、資源が希望する構成に準拠するかを評価する。管理ルールとカスタムルールがあり、評価の条件を目的に合わせる。構成の記録、記録した構成の評価、実際の資源への修復を分けて考える。

StartConfigRulesEvaluationは最後に把握した構成を使って再評価する。最新の資源構成を再記録する操作ではない。記録後にタグが変更された場合、再評価を呼んだだけで最新タグを評価したとは扱わず、記録時点と現物の状態を確認する。

## 比較・条件

| 工程・設定 | 確認するもの | 混同を避けるもの |
| --- | --- | --- |
| 構成の記録 | 対象と記録時点・鮮度 | 再評価で必ず最新取得 |
| Configルール | 希望する構成と評価条件 | 資源の書換えそのもの |
| オンデマンド評価 | 最後の記録に対する結果 | 最新構成の再記録 |
| 修復設定・実行 | 対象・権限・承認等と実結果 | NON_COMPLIANTだけで完了 |

## 対処・限界

不適合は対処の必要を示す評価であって、自動修復完了の証拠ではない。修復には別の設定があり、対象SSM文書と利用権限等を確認する。修復後の実状態・記録・評価も確認し、表示だけを適合へ変える対処にしない。

同じルールの既存オンデマンド評価が完了してから次の評価を開始する。新規ルールは作成時に評価されるため、作成直後に再評価APIが常に必須とは説明しない。CloudTrailの操作監査、CloudWatchの性能観測とも目的が異なる。

全記録モード、管理ルール固有の評価条件、組織/サービス連携ルールの制約、修復の再試行と権限、料金、実AWS試験は未確認。自動修復は評価スナップショットに依存し、最新の実状態が適合していても古い不適合結果に基づいて開始される場合がある。実状態と対処の影響を確認する。修復設定を作成しただけで、その実行や業務安全性を保証しない。

## ケース問題・誤答理由

第1問はタグの現物と記録が異なる状況、第2問は別ルールで修復が未設定。再評価を再取得へ読み替える誤答、評価結果を修復完了へ読み替える誤答を説明する。

## 用語・補足

**準拠**は希望する条件に合っていること。**NON_COMPLIANT**は条件に適合しない評価。**修復**は実際の構成を変更する対処。**SSM文書**はSystems Managerで実行する処理の定義。**鮮度**は判断に使う記録がどの時点の状態かという観点。
