# MFA：認証条件と操作権限を分ける

学習目標：MFAによる認証の強化が、対象操作の許可を代わりに与えるものではないと説明する。既存単位 `mfa` の本文。前提は認証。関連章：ch02、ch10。

## 仕組み

MFAは複数の要素で認証する考え方である。ここではIAMユーザーがAPI用の一時認証情報を取得する場合に絞り、MFAデバイスの識別とそのデバイスが生成したコードを使う。IAMユーザーの長期キーを使うAPI要求を、コンソールのパスワードとコードによるログインと同一視しない。

GetSessionTokenではIAMユーザーの長期認証情報に加え、MFAデバイスの識別子と正しいコードを提示し、MFA認証を伴う一時認証情報を得られる。誤ったMFAコードはアクセス拒否となる。返される権限は元のIAMユーザーの権限に基づき、MFAが削除や管理者操作の権限を追加するわけではない。

AssumeRoleにもMFA情報を渡せる。ロールの信頼ポリシーがMFAの存在を条件として要求する場合、その条件を満たす必要がある。特にIAMユーザーの長期キーで直接AssumeRoleする場面で、必要なMFA情報を付けずに「デバイスは登録済みだから十分」と判断しない。

流れ：IAMユーザーの認証情報とMFAコード → STSの認証・信頼条件 → 一時認証情報 → 対象操作の許可を別に評価。MFAの登録、実際の要求がMFA条件を満たすこと、操作を許可することは別の段階である。

## 条件・比較・限界

| 対象 | 何を満たすか | 代替できないもの |
|---|---|---|
| MFAデバイスの登録 | 利用するデバイスを用意する | 実際のAPI要求に必要なMFA情報 |
| MFA情報付きGetSessionToken | MFA認証を伴うユーザーのセッション取得 | ユーザーが持たない操作権限 |
| MFA条件付きの信頼ポリシー | ロール引き受け時の認証条件 | ロールのS3などへの操作許可 |
| 最小権限 | 対象・操作・条件を絞る | 認証要素を増やすこと |

IAMユーザーのAPI認証を扱う範囲で、フェデレーション先やIdentity CenterのMFA設定手順、パスキー等の方式比較、MFA耐性の定量評価は別の資料が必要。MFAを登録しただけで、すべての長期キーによるAPI要求にMFAが自動必須になるとは教えない。利用経路とポリシー条件を確認する。

GetSessionTokenの一時認証情報には呼び出せるIAM/STS操作の制約もあるので、「ユーザーの権限が基礎」という説明を任意のAPI成功の保証にしない。ルート認証情報によるGetSessionTokenは公式説明でも推奨されず、返される認証情報はルートの権限を持つ。短命化やMFAを理由に日常作業でルートを使う方向へ誘導しない。

## ケースと条件変更

`knowledge/game-cases.json` の `mfa-api-session` が正本。第1問は正しいMFAコード付きのGetSessionToken取得、第2問は別の要求として長期キーでAssumeRoleし、必要なMFA情報を欠く場合を扱う。第1問に正解したことや、そこで得た認証情報を第2問で使うことを前提にしない。

条件変更：正しいMFA情報でセッションを取得しても、元のIAMユーザーに対象写真の削除許可がない。MFAはその許可を追加しない。不要な操作を許可せず、業務上必要な対象・操作を別途評価する。

確認問題はMFAと最小権限の役割、および従業員への委任で認証条件と必要な権限を併用する判断。本人のMFA登録状況や理解状況はこの教材から推測しない。
