# 最小権限：対象と操作を絞り、検証の範囲を確かめる

学習目標：必要な対象・操作・条件に許可を限定し、その検証結果がどこまでを確認したか説明する。既存単位 `least-privilege` の本文。前提は認可とIAMロール。関連章：ch02、ch05、ch10。

## 仕組み

Actionは許可する操作、Resourceはその操作の対象、Conditionは必要な場合の要求条件を絞る。アプリが動くという理由だけで全サービス・全操作・全リソースへ許可を広げたままにしない。必要な要求を具体化し、操作と対象をセットで確認する。

例として、写真加工アプリが汎用S3バケット `example-photo-deliveries` の `outputs/` 配下へ、タグやACLを指定せず保存するだけなら、候補ポリシーはs3:PutObjectと対象のオブジェクト範囲に限定する。バケット名は架空の例で、実AWSへ適用した設定ではない。

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:PutObject",
    "Resource": "arn:aws:s3:::example-photo-deliveries/outputs/*"
  }]
}
```

この例は要求を限定した比較用で、SSE-KMS、タグ・ACL指定、ほかの権限・Deny、所有権や実行経路は別に評価する。タグ集合も指定するならPutObjectTagging等の必要許可を見直す。実行できないからといって、原因を特定せずs3:*や管理者権限へ拡張しない。

## 検証の流れと限界

IAMのSimulatePrincipalPolicyは主体のポリシーとAPI操作、リソース、必要なコンテキスト値を組み合わせ、許可・拒否をシミュレートする。APIを実行しないし、存在しないリソースもシミュレートできる。Conditionを使うなら、どのコンテキストキーと値を評価に与えたかも記録する。

流れ：実行したい要求を列挙 → Action/Resource/必要なConditionを絞る → 許可すべき要求と拒否すべき要求をシミュレート → 対象の実環境でも期待する結果を検証する。

結果は実環境と異なる場合がある。リソースポリシーは自動取得されない等のシミュレーター側の制約もあり、使った入力を確認する。シミュレーションのAllowは写真が実際に保存されたという証拠でも、ほかの操作が全て拒否されたという証拠でもない。

## 比較・条件

| 選択 | 満たす点 | 代償・不足 |
|---|---|---|
| 必要なPutObjectとoutputs配下だけ | 指定業務の対象・操作へ絞る | 要件変更時の見直しと検証が必要 |
| 同じ保存先へs3:* | 保存要求を含む広い許可 | 不要な読取・削除等まで広げる |
| PutObjectを全バケットへ | 操作は限定される | 業務外の保存先にも対象を広げる |
| シミュレーターのAllowだけで完了 | 入力したポリシーの判断を得る | 実行、通信、実環境全体の成功は未確認 |

変更する主体・対象・要求条件を特定してから比較する。短命な認証情報、MFA、アクセス許可境界はそれぞれ役割が異なり、単独で必要最小限の実行権限を自動決定するものではない。

## ケース・転移・確認

`knowledge/game-cases.json` の `least-privilege-photo-simulation` が正本。第1問は限定した保存要件に対する3案の不要な許可を比較し、第2問はAllowというシミュレーター結果の意味を問う。第2問は第1問の正答を前提としない。

条件変更：保存する要求にタグ集合を追加する。必要なタグ付与の操作許可を再確認し、対象範囲は引き続き業務の保存先に絞る。要件が増えたことを理由に全S3操作を許可しない。

説明問題は対象・操作・条件の3軸、適用問題は写真保存だけのアプリへ不要な読取や削除を与えない判断。許可すべき操作だけでなく、業務外の対象と操作を拒否できるかも確認する。
