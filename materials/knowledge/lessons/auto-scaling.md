# Auto Scalingの希望容量と最小・最大境界

## 到達目標

最小・最大・希望容量と、実際の起動/処理準備を分ける。既存第4章原稿のauto-scaling素材を、境界変更時の具体的な判断へ詳述する。

## 仕組み

ASG（Auto Scalingグループ）はEC2の容量を管理する単位。DesiredCapacity（希望容量）は維持を試みる容量で、MinSize（最小）以上、MaxSize（最大）以下で設定する。作成時に希望を指定しなければ最小値が使われる。最大値は常に起動する容量ではない。

ここでは1台=1容量単位、重み付き混合構成を使わない通常の台数指定に限る。希望容量の設定と、実際の起動・ヘルス確認・アプリ準備完了は別。容量の確保失敗や準備遅延もあるため、値だけでサービスの処理能力が確保できたとは扱わない。

```mermaid
flowchart LR
  B[最小・最大の設定範囲] --> D[希望容量]
  D --> C[容量の維持を試みる]
  C --> H[実際の起動・ヘルス・アプリ準備を確認]
```

UpdateAutoScalingGroupで希望を指定せず境界だけを変える場合にも注意する。新MinSizeが現在サイズより大きければ希望容量はその新MinSizeへ変わる。新MaxSizeが現在サイズより小さければ希望容量はその新MaxSizeへ変わる。現在3で最小を4へ上げる例と、現在5で最大を3へ下げる例は、同じ希望を固定したままの変更ではない。

希望容量を現在サイズより小さくして縮退が起きれば、終了ポリシーで終了対象を決める。縮退の前に実行中処理・ローカルデータ・セッションをどう保護するかを検討する。終了対象や終了時刻を希望容量だけで断定しない。

## 比較・条件

| 設定/状態 | 意味 | 混同しないもの |
| --- | --- | --- |
| 最小容量 | 希望容量の下限 | すべての変更で現在台数と同じになるわけではない |
| 最大容量 | 希望容量の上限 | 常に起動すべき容量ではない |
| 希望容量 | 維持を試みる容量 | 瞬時のアプリ準備完了ではない |
| 現在サイズ | 更新条件で比較する実際のグループサイズ | 最新の希望値と常に同じとは限らない |

最大容量だけを増やしても最大まで増台する指示ではない。必要な希望容量やスケーリングポリシー、実際に確保できた容量を別に確認する。台数変更を、ALBの振り分け設定やデータ複製の代替として扱わない。

## 限界・例外

重み付き混合構成では容量単位と台数が一致せず、MaxSizeを超える例外が公式説明にある。属性ベースのvcpu/memory-mib容量、AZ再配分や置換時の一時超過、ウォームプール、終了保護、停止プロセス、インスタンス更新は本単位の確認範囲外。通常の台数例を「どんな場面でも現在台数は最大を超えない」という一般規則にしない。

## ケース問題・誤答理由

正本は `knowledge/game-cases.json` の `asg-capacity-boundary`。第1問は最小の引上げ、第2問は最大の引下げ。希望が絶対に変わらないという誤答は更新APIの条件を無視する。最大まで常に起動、全台終了という誤答は境界値と実際の変更を混同する。変形問題では最大の引上げだけを扱う。

## 用語・補足

**容量単位**は設定値の測定単位で、通常の例では1台を1と数える。**スケールアウト**は容量を増やすこと、**スケールイン（縮退）**は減らすこと。**終了ポリシー**は縮退時にどのインスタンスを終了するかを決める設定。料金節約や無停止を台数変更だけで保証しない。
