AWSの全体像

サービス名より先に、置き場所・責任・障害の範囲を理解します。

リージョンとAZ

身近なたとえ

リージョンを都市、AZを別々の電源を持つ拠点として考えます。

仕組み

リージョンは地理的な区分、AZはリージョン内の独立した場所です。EC2を同じAZに増やしても、そのAZ全体の障害には弱いままです。複数AZへの配置とリクエストの切り替えを組み合わせて可用性を設計します。リージョン選定では利用者との距離、データ保管要件、サービス提供状況も確認します。

リージョン
├ AZ-A → EC2-A
└ AZ-B → EC2-B

選ぶポイント

  • AZ分散とリージョン分散は障害範囲が異なる。
  • リソースは原則として他リージョンへ自動複製されない。
  • 確認：同じAZでサーバーを2台にするとAZ障害を防げる？ → 防げない。

Multi-AZ

AZ障害への備え
注意：アプリとデータ両方の冗長化が必要

Multi-Region

リージョン障害への備え
注意：複製と切り替えの設計が増える

公式出典（確認日 2026-10-05）：AWS公式: regions

責任共有モデル

身近なたとえ

建物の管理者が設備を守っても、部屋の鍵と中の書類は利用者が管理します。

仕組み

AWSは物理施設やクラウド基盤を守ります。EC2のゲストOSの更新、アプリケーション、権限設定は利用者側です。S3のようなマネージドサービスでも、データ分類とアクセス権の責任は残ります。責任の境界は利用するサービスによって変わるため、「AWSに置けばすべて安全」と判断しないことが大切です。

AWS → 施設・物理ホスト・基盤
利用者 → データ・権限・アプリ
EC2利用者 → ゲストOSも管理

選ぶポイント

  • 管理作業が減っても利用者の責任がなくなるわけではない。
  • 確認：S3のデータを誰に公開するか決めるのは？ → 利用者。

EC2

OSまで自由に構成
注意：OSの保守が必要

マネージドDB

保守の一部をAWSへ任せる
注意：データと権限は利用者が管理

公式出典（確認日 2026-10-05）：AWS公式: responsibility

要件から構成を選ぶ

身近なたとえ

車を選ぶとき、最高速度だけでなく人数・安全性・予算を比較するのと同じです。

仕組み

SAAの問題では、障害に耐える範囲、応答時間、管理負荷、費用を分けて読みます。「最小コスト」でも停止できない処理に中断される実行基盤を選ぶことはできません。まず必須条件を満たす候補を残し、その中で費用や運用負荷を比較します。処理台数を増やす設計では、セッションを1台だけに閉じ込めない工夫も必要です。 EC2は仮想サーバー、S3はオブジェクト保存、RDSはDB管理のサービスです。一時データと失いたくない結果を分け、EC2のインスタンスストアには再生成できる一時データを置きます。停止や終了で失う可能性があるため、処理結果はS3などへ保存します。Spotは中断される場合がある購入方式なので、チェックポイントと再投入を設計できる処理に向きます。

要件 → 必須条件を抽出
→ 不適合な候補を除外
→ コスト・運用で比較

選ぶポイント

  • 可用性は動き続ける性質、耐久性はデータを失いにくい性質。
  • 複製だけでは誤削除から戻せるとは限らない。
  • 確認：停止不可の唯一のサーバーをSpotだけで構成してよい？ → 中断への備えが必要。

スケールアップ

1台を大きくする
注意：1台への依存が残る

スケールアウト

複数台に処理を分ける
注意：状態と負荷分散を設計する

公式出典（確認日 2026-10-05）：AWS公式: regions ／ AWS公式: ec2 ／ EC2インスタンスストア

IAMとアクセス制御

誰が、何に、何をできるかを最小限に定めます。

ユーザー・ロール・一時認証情報

身近なたとえ

社員証を共有する代わりに、作業中だけ有効な入館証を渡すイメージです。

仕組み

IAMロールはサービスや人が引き受ける権限の器です。EC2上のアプリにアクセスキーを埋め込む代わりに、必要なS3操作だけ許可したロールを利用します。人のアクセスではフェデレーションやIAM Identity Centerを使い、一時認証情報とMFAを基本にします。ルートユーザーは日常作業に使いません。 MFAはパスワードに加えて別の認証要素を求める仕組みです。ルートユーザーをMFAで保護し、日常業務は必要な権限に絞った別のIDで行います。

人・EC2 → ロールを引き受ける
→ 有効期限付き認証情報
→ 許可されたAWS操作

選ぶポイント

  • ロールの信頼ポリシーは誰が引き受けられるかを決める。
  • 権限ポリシーは引き受けた後の操作を決める。
  • 確認：EC2のソースコードに固定キーを保存する？ → インスタンスロールを使う。

IAMユーザー

必要時に長期IDを管理
注意：長期キー管理の負担

IAMロール

一時的なサービス・人の権限
注意：信頼関係と権限の両方を設定

公式出典（確認日 2026-10-05）：AWS公式: iam ／ AWS公式: role ／ AWS公式: sts

Allow・Denyと最小権限

身近なたとえ

許可証があっても、立入禁止の部屋には入れません。

仕組み

IAMでは明示的なDenyがAllowより優先します。許可がない場合も原則拒否されます。Action、Resource、Conditionを絞り、必要な操作だけを与えます。SCPやアクセス許可の境界は付与可能な権限の上限であり、それだけで操作を許可しません。ポリシー評価にはリソースポリシーやセッション種別による違いがあるため、単純な足し算だけで判断しないようにします。

要求 → 明示的Denyあり？ → 拒否
→ 許可と各種制約を確認
→ 条件を満たした操作だけ許可

選ぶポイント

  • S3バケット自体とオブジェクトはResourceの指定が異なる。
  • ワイルドカードは必要性を確認する。
  • 確認：SCPでAllowしただけでEC2を起動できる？ → IAM側の許可等も必要。

権限ポリシー

具体的な操作を許可
注意：明示的Denyを上書きできない

SCP

組織の上限を設定
注意：単体では権限を付与しない

公式出典（確認日 2026-10-05）：AWS公式: policy ／ AWS公式: scp ／ AWS公式: boundary

アカウントをまたぐ安全な委任

身近なたとえ

別会社へ合鍵を渡す代わりに、対象と期限が決まった受付手続きを設けます。

仕組み

別アカウントの担当者にはクロスアカウントロールを用意します。信頼ポリシーと呼び出し側の権限を整え、外部業者が複数顧客を扱う場合はExternal IDで混乱した代理問題に備えます。人のログインをまとめるIAM Identity Centerと、アプリ利用者の認証を扱うCognitoは用途が異なります。権限は継続的に見直し、不要なアクセスを減らします。

利用元アカウント → STS AssumeRole
→ 利用先の信頼ポリシーを評価
→ 対象ロールの権限で操作

選ぶポイント

  • アクセスキーの共有で委任しない。
  • External IDはパスワードではなく顧客の取り違えを防ぐ条件。
  • 確認：取引先へ自社ルートキーを渡す？ → 限定ロールで委任する。

Identity Center

従業員のAWSアクセス
注意：一般消費者向け会員基盤とは別

Cognito

アプリ利用者の認証
注意：AWS管理者用統合アクセスとは別

公式出典（確認日 2026-10-05）：AWS公式: external ／ AWS公式: identity ／ AWS公式: cognito

用語集

リージョン

AWSの地理的な提供地域。遅延、データの所在、サービスの提供状況を考えて選ぶ。

アベイラビリティーゾーン（AZ）

リージョン内の独立した場所。複数AZへの構成で、1つのAZの障害に備える。

責任共有モデル

AWSと利用者で安全性や運用の責任を分担する考え方。利用するサービスで境界が変わる。

可用性

必要なときにサービスを利用できる性質。冗長化と切り替えを組み合わせて高める。

耐久性

保存したデータを失いにくい性質。サービスが今応答できるかを表す可用性とは異なる。

スケーリング

負荷に合わせて処理能力を変えること。1台を大きくするスケールアップ、台数を増やすスケールアウトがある。

Spotインスタンス

中断の可能性があるEC2の購入方式。中断しても再開できる処理などでコスト削減を検討する。

インスタンスストア

EC2ホストに直接接続された一時的なストレージ。停止・終了などによる消失に備え、唯一の永続データを置かない。

Amazon S3

データをオブジェクトとして保存するサービス。アクセス権とデータ管理は利用者が設計する。

Amazon RDS

リレーショナルデータベースの管理サービス。基盤保守の一部をAWSに任せられるがデータ・権限の管理は残る。

IAMロール

人やサービスが引き受ける権限のまとまり。信頼ポリシーで誰が引き受けるか、権限ポリシーで何ができるかを定める。

一時認証情報

有効期限を持つAWS操作用の認証情報。長期アクセスキーの配布を減らせる。

最小権限

必要な対象に必要な操作だけを許可する原則。Action、Resource、Conditionなどを絞る。

明示的Deny

ポリシーで明示的に禁止する指定。対象操作に適用されればAllowより優先される。

サービスコントロールポリシー（SCP）

Organizationsのメンバーアカウントで利用できる権限の上限を定める。SCP単体では操作権限を付与しない。

クロスアカウントアクセス

別のAWSアカウントのリソースへアクセスすること。ロールによる委任などで信頼関係と権限を設定する。

External ID

外部事業者が複数顧客のロールを使うとき、顧客の取り違えを防ぐ信頼ポリシー条件。秘密のパスワードではない。

IAM Identity Center

従業員の複数AWSアカウントや業務アプリへのアクセスをまとめて管理するサービス。

Amazon Cognito

一般利用者向けアプリの認証などを扱うサービス。ユーザープールでサインアップとログインを提供できる。

ルートユーザー

AWSアカウントの強い権限を持つ主体。MFAで保護し、日常作業は別の適切なIDで行う。

多要素認証（MFA）

パスワードに加えて別の認証要素を求める仕組み。パスワードだけの漏えいに対する防御を加える。
