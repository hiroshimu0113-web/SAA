# SAA学習プロジェクト：エージェント実行向け設計・タスク計画

## 1. 進め方の修正

人日ベースの見積もりを外し、**エージェントが成果物を作成・検証し、完了条件を満たしたタスクから積み上げる方式**に変更する。

ユーザーが教材を執筆したり、コードを書くことは前提にしない。ユーザーの担当は、学習体験へのフィードバック、iPhone実機での確認、必要なアカウント操作とする。

基本方針は維持する。

- AWS初学者向けの日本語教材。1日20〜30分。
- iPhoneでオフライン利用できるPWA。
- 独自テキスト12章、通常問題200問、模擬試験65問×2回。
- 教材完成後に、AWS構成をカードで組むゲームを追加。
- React・TypeScript・Vite、端末内保存、無料枠での静的配信を基本とする。
- ログイン・端末間同期・App Store配信は初版の対象外。

**教材を使い始められることを最初の到達点とし、全教材やゲームの完成を待たない。**

## 2. タスクの管理・完了ルール

実装開始時に、エージェントが次の管理資料を作る。

| 成果物 | 役割 |
|---|---|
| `docs/PROJECT.md` | 目的、構成、仕様、対象外、決定事項 |
| `docs/TASKS.md` | タスクの依存関係、状態、成果物、検証結果 |
| `docs/CONTENT_MAP.md` | AWS公式試験範囲と教材・問題の対応 |

各タスクには、以下を必ず記載する。

- **ゴール**：何ができる状態にするか。
- **前提**：先に完了すべきタスクと参照資料。
- **成果物**：作成・更新する教材、コード、仕様など。
- **完了条件**：確認可能な振る舞い、数量、品質条件。
- **検証結果**：実施した確認と結果、未確認事項。
- **引き継ぎ**：次のタスクが利用する情報と残課題。

状態は「未着手／実行中／検証待ち／完了／ブロック」で管理する。**作成しただけでは完了にせず、完了条件の検証までを担当エージェントの仕事とする。**

複数の独立した成果物がある、または一度に検証しにくいタスクは子タスクへ分割する。子タスクが完了するまで親タスクは完了にしない。

## 3. 教材版の実行タスク

### フェーズA：制作・開発の基準を確定する

| ID | タスクと成果物 | 完了条件 | 依存 |
|---|---|---|---|
| A1 | **試験範囲を固定する**：最新のAWS公式試験ガイドを確認し、12章への対応表を作成 | 全試験タスクに学習先があり、出典・確認日を記録している | なし |
| A2 | **教材の形式を固定する**：レッスン、用語、問題、出典の形式と品質チェック項目を作成 | 見本レッスン1本・単一選択と複数選択の見本問題が共通形式で表現できる | A1 |
| A3 | **アプリの仕様を固定する**：画面遷移、保存・更新・バックアップ仕様を作成 | 初回利用からオフライン学習・復元までの操作と失敗時の挙動が決まっている | A2 |

教材は「たとえ→正式な仕組み→構成図→使い分け→確認問題」を基本とする。問題には各選択肢の解説、関連概念、公式出典を必須にする。

### フェーズB：iPhoneで学習できる最小版を作る

| ID | タスクと成果物 | 完了条件 | 依存 |
|---|---|---|---|
| B1 | **アプリの土台を作る**：画面構成、教材表示、ホーム画面追加用設定 | ビルドが成功し、スマートフォン幅で見本教材を読める | A3 |
| B2 | **最初の教材を作る**：AWSの全体像・IAMの2章と20問 | 出典照合済みで、全問に正解・誤答理由がある | A2 |
| B3 | **演習を成立させる**：回答、採点、解説、履歴保存 | 単一／複数選択を正しく採点し、再起動後も履歴が残る | B1、B2 |
| B4 | **オフライン学習を成立させる**：教材一括保存、保存状態表示、更新処理 | 未閲覧教材も通信なしで開き、更新失敗時にも旧版を使える | B3 |
| B5 | **履歴を保護する**：JSON書き出し・復元 | 復元後の履歴が一致し、不正ファイルで既存データを壊さない | B3 |
| B6 | **iPhone利用版を配信・検証する**：HTTPS配信と実機確認手順 | ホーム画面から機内モードで起動し、読む・解く・解説表示・履歴保存ができる | B4、B5 |

**B6完了が最初のリリース地点。ここからユーザーが日常学習を始める。**

実機をエージェントが操作できない場合は、ユーザーに短い確認手順を渡す。PCの検証完了と実機確認待ちを区別し、実機で確認していない動作を確認済みとはしない。

### フェーズC：教材と試験対策を完成させる

教材制作は、一括の巨大タスクにせず、以下の単位で管理する。

| タスク単位 | ゴール・完了条件 |
|---|---|
| **章ごとの教材作成 ×12** | 短いレッスン、構成図、比較表、関連用語を作り、担当する試験範囲を説明できる。最小版の2章は再利用する |
| **通常問題20問単位 ×10** | 合計200問。各問の正解が要件から導け、誤答理由・公式根拠・関連教材がそろう。最小版の20問を含む |
| **用語集の統合 ×1** | 章で導入した用語に説明と教材リンクがあり、重複・表記揺れを解消する |
| **復習・検索機能 ×1** | 誤答と自信なしの問題を復習でき、教材・用語をオフライン検索できる |
| **模擬試験作成 ×2** | 各65問。通常問題と重複させず、4分野の出題比率を概ね反映し、全問を検証する |
| **模擬試験機能 ×1** | 制限時間、途中保存、提出後の採点・分野別結果・解説表示が動く |
| **教材全体の監査 ×1** | 試験範囲の抜け、矛盾、重複、根拠不足、参照切れを確認し、発見した不備を修正する |

A1で章別の問題数を配分し、各20問バッチの担当範囲を確定する。教材作成後に対応する問題を作り、作成と検証を分けて実施する。

**出典で確認できない説明や、正解が一意に決まらない問題は公開対象に入れず、修正タスクに戻す。**

## 4. ゲームの実行タスク

教材完成を依存条件とし、まず小さな試作で学習効果と遊びやすさを確認する。

| ID | タスクと成果物 | 完了条件 | 依存 |
|---|---|---|---|
| G1 | **ゲームルールを固定する**：ターン進行、配置、予算、勝敗、カード効果、教材との対応 | 具体的な手札と障害から結果を計算でき、未定義のルールがない | 教材完成 |
| G2 | **短い冒険を作る**：カード8枚・3戦・結果解説 | 開始から勝利／敗北まで遊べ、判断したAWS概念を振り返れる | G1 |
| G3 | **中断・再開を保証する**：ターンごとの自動保存 | オフラインで終了・再起動しても確定済みターンから再開できる | G2 |
| G4 | **試作を評価・修正する**：自動検証とプレイ確認 | 行動不能、成立しない勝利条件、AWSの誤解を生む表現を解消する | G3 |
| G5 | **ゲーム初版へ拡充する**：20枚、通常シナリオ6種類、ボス1種類、分岐と報酬 | 1回10〜15分を目標に冒険が成立し、関連教材へ移動できる | G4 |

現実のAWSの役割とゲーム内効果は分けて表示する。ゲーム内の予算・性能値は学習用の抽象値とし、実料金や実測性能として扱わない。

G5は「カード追加」「シナリオ追加」「分岐・報酬」「全体調整」の子タスクに分け、個別に検証する。

## 5. エージェントの運用と進捗報告

親エージェントがタスク管理・仕様整合・統合検証を担当する。必要に応じて、教材作成、問題作成、アプリ開発、レビューをサブエージェントに委任する。

- 仕様の確定と依存関係のある作業は順番に進める。
- 共通形式が決まった後の章別教材など、独立した作業は並行化する。
- 同じファイルの同時編集を避け、担当成果物を明確にする。
- 教材・問題は作成担当とは別のレビュー工程を通す。
- 通常の実装判断は確定仕様に従って進め、タスクごとの開始承認は求めない。
- アカウント権限や実機操作が必要な場合のみ、必要な操作を具体的に依頼する。

進捗は時間や主観的な割合ではなく、次の形式で報告する。

> **完了**：B3。20問の採点と再起動後の履歴保持を検証済み。  
> **次の作業**：B4。全教材のオフライン保存と更新失敗時の動作を実装。  
> **確認待ち**：B6のiPhone実機確認。  
> **利用可能な成果物**：教材2章・問題20問のプレビュー。

タスクが想定より大きいと分かった場合は、エージェントが子タスクに分け、依存関係と完了条件を更新する。**工程を省略して完了扱いにせず、使える成果物と検証結果を積み上げる。**
